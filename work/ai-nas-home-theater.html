Making local AI actually useful at home.

Worked on an AI-powered NAS platform combining local models, intelligent file management, media discovery, privacy controls, and AI agents — during a 0→1 build that won the CES Asia Best Innovation Award.

Problem

What wasn’t working

Local AI systems had powerful capabilities but poor discoverability, unreliable tool calling, and unclear user value. The on-device agent could technically do a lot — but nobody could tell, and it kept timing out.

User Insight

What the user actually needed

Users did not want “AI features.” They wanted AI to remove friction from things they already cared about — media, files, photos, and privacy. The product had to disappear into an existing habit, not add a new one.

My Role

What I owned

  • Interviewed 100+ NAS users to separate real product opportunities from feature requests.
  • Prioritized the roadmap for the AI NAS business unit inside a company-wide incubator, competing against ~100 other internal projects for investment.
  • Designed and validated the AI Home Theater experience end to end, from concept through a 3-iteration beta.
  • Owned model selection for the on-device agent and diagnosed a scaling defect in its tool-calling architecture.
  • Defined the privacy architecture that separated a fully offline volume from a connected service volume.
  • Built a working prototype of the Home Theater experience myself (FastAPI + SQLite + vanilla JS/CSS, zero build step) — continue-watching shelf, movie/series grouping, HTTP-range video streaming — to validate the UX before it became a funded roadmap item.
  • Reverse-engineered the protocol for an undocumented secondary display panel (USB-serial, no public spec) and built its driver end to end, turning it into a configurable dashboard — at roughly 80% lower cost than sourcing the OEM's own accessory.
Constraints

What had to be true

  • Everything had to run acceptably on consumer NAS hardware, not a cloud GPU cluster.
  • Privacy was a stated product pillar, not a compliance checkbox — the architecture had to hold up under real scrutiny.
  • The agent's tool registry was growing faster than its ability to reason about which tool to call, and every added integration made timeouts more likely.
Decision Process
01

Finding the real opportunity

Rather than starting from “what can the AI do,” I ran structured interviews with 100+ existing NAS users to map where they actually lost time: finding a movie to watch, organizing a media library, recovering from duplicate or misnamed files.

Home Theater — AI-assisted media discovery and recommendation — surfaced as the clearest, most testable opportunity, so I scoped an MVP around it instead of a broader “AI assistant” pitch.

02

Diagnosing the timeout problem

Agent timeouts and runaway token use traced back to exhaustive API enumeration — the agent was reasoning over every available tool on every turn.

I proposed an MCP-based tool registry so the agent only reasoned over relevant tools per task, cutting tool-selection token overhead by roughly 80% and eliminating the timeouts outright.

03

Choosing the on-device model

Model choice had to balance quality, latency, and what would actually run on-device. I built a 6-dimension evaluation framework and A/B tested 7 candidate LLMs across 1,000+ prompts.

Qwen paired with Hermes scored highest (4.5/5) and became the on-device default; the same evaluation harness later caught 40+ release-critical defects before they reached users.

04

Prototyping before the roadmap slot

Rather than writing a spec and waiting for an engineering slot, I built Home Theater myself as a working prototype: a FastAPI backend with a single SQLite table for metadata, HTTP-range streaming so video could scrub and resume, and a shelf-based UI (Continue Watching, Recently Added, Movies, TV Series) in plain HTML/CSS/JS with no build step.

That let the 80-user beta touch a real, working product in days rather than after a full engineering cycle — the usage data from that prototype, not a mockup, is what won the case for full-scale investment.

Solution

What shipped

  • An AI Home Theater experience: on-device recommendations for similar titles, actors, and directors, plus IMDb-based subtitle matching, wrapped in a simple conversational entry point.
  • Auto Scan — ingestion-time indexing and tagging that cut manual organization and retrieval time by 90%.
  • An MCP-based tool registry that scoped the agent's available tools to the task at hand instead of the full catalog.
  • Continue-watching and movie/series grouping (with per-season episode lists), so the experience read as a home-theater app, not a file browser with a play button.
Shipped
Technical Architecture

How it was built

  • Dual-volume privacy design: an isolated private volume for fully offline data and models, and a separate connected-service volume for anything that touches the network — so users could opt into convenience without quietly losing the offline guarantee.
  • On-device inference (Qwen + Hermes) for recommendation and conversational features, with the MCP tool registry mediating access to file-system and media-metadata tools.
  • A reproducible evaluation harness (1,000+ prompts across 7 models) used both for model selection and as an ongoing regression suite.
  • The wider platform separated into an Agent layer (task planning, dynamic skill loading), a Model layer (a local, quantized multi-billion-parameter LLM with multimodal understanding), a Data layer (private RAG over the user's own files, vector search, full-disk encryption), and a Connection layer (NAT traversal so the NAS is reachable without a public IP) — Home Theater was the consumer-facing surface I built on top of that stack.
  • My own prototype ran on FastAPI with one evolving SQLite table — new columns added through idempotent migrations, never a breaking schema change — and HTTP Range requests for scrubbing and resume: deliberately boring, well-understood tech so the team could argue about the experience, not the plumbing.
Product Decisions

Trade-offs I made on purpose

  • Shipped Home Theater as a narrow, well-tested wedge rather than a broad “AI assistant,” so the team could validate real usage before expanding scope.
  • Treated the tool-calling defect as a product problem, not just an engineering bug — an agent that times out has no product value regardless of model quality.
  • Made privacy a structural property of the architecture (separate volumes) rather than a setting a user could misconfigure.
  • Chose to prototype in a throwaway stack (FastAPI/SQLite/vanilla JS) rather than wait for the production platform, so real usage could shape the roadmap instead of the other way around.

What I Learned

Takeaways

  • A model-quality problem and a product-adoption problem can look identical from the outside — the fix here was architectural (tool scoping), not a bigger model.
  • Validating one sharp use case with real usage data made the case for full-scale investment far more effectively than a broader feature list would have.
  • A rough, working prototype moves a roadmap conversation faster than the best-written spec — it turns “I think users will like this” into something a stakeholder can actually click through.
Also shipped

An auxiliary-display driver for an undocumented USB panel

The NAS's secondary display — a small USB LCD bar — had no public protocol or SDK. I reverse-engineered its serial framing (a 5-byte header plus a raw JPEG, no container) and built a driver that turns it into a configurable dashboard.

Scenes — industrial telemetry, NAS status, a clock, weather, now-playing, a drag-to-arrange custom widget board, even a media loop or photo slideshow — are authored as ordinary HTML pages, screenshotted headlessly, rotated into the panel's native orientation, and streamed over serial. A new scene never needs a firmware change or a rebuild.

Reported result: roughly 80% lower cost than sourcing the OEM's own accessory driver, for a materially more flexible display.
